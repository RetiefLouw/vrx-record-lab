The score is simple. The proof is not.

The League of Robot Runners (LoRR) turns multi-agent path finding into a throughput race: finish as many revealed tasks as possible before the fixed simulation clock ends, while keeping every action valid and every planner call inside its budget.

01 / challenge

LoRR is a factory floor for 100 robots.

A shared grid contains agents, obstacles, and a stream of pickup-and-delivery tasks. Agents must move without collisions, collect work, and return it to the right destination. The system is scored by completed work, not by how elegant a single path looks.

world

Grid + task stream

The 2024 benchmark supplies a fixed public instance. Tasks are revealed at release times, so a planner cannot precompute the whole future.

action model

MAPF-T actions

At each tick, every agent can move forward, turn, or wait. A joint plan must remain collision-free and executable by the runtime.

objective

Throughput under a clock

At the makespan, the evaluator records numTaskFinished. Higher is better; errors and timeouts are evidence that the run was not clean.

Why this target is useful. Unlike the historical VRX phase-3 record, LoRR exposes the instance, evaluator lineage, best-known solution, team identity, and source commit. The loop is CPU-feasible, so one hypothesis can be tested, audited, and rejected in minutes.

02 / archive context

The official 2024 Benchmark Archive is the reference layer: it names the instance, reports the best-known task count, and points to a team’s archived solution. The local evaluator is the replay layer. Those layers must be shown separately.

Score semantics. LoRR’s leaderboard quantity is the integer numTaskFinished for the declared agent count and simulation time. It is not a weighted scalar and is not numerically comparable to VRX pose error or BARN’s success/time score. The archive’s number remains the authoritative published reference even when a replay on another runtime produces a different count. 03 / execution loop

Every tick is a negotiation between work and time.

The planner does not receive an unlimited offline budget. It must schedule new work, search for collision-free paths, execute a short window, and return control before the next deadline.

LoRR run lifecycle · reveal → assign → plan → execute → score

The important engineering tension is visible in the loop: a longer search may find better paths, but a late planner call can become an entry timeout and erase the throughput gain.

Planner errors

Failures in the planning path. A clean promotion target keeps this at 0.

Schedule errors

Failures in assigning work or producing a valid schedule. The same clean gate is 0.

Entry timeouts

Deadline misses at the runtime boundary. Q-35 and Q-36 are valuable because both reached 0 here under pinned execution.

07 / next innovation path

Turn the margin into a mechanism.

Q-35 and Q-36 close the first reproducibility question under a pinned runtime. The next result should now isolate why the Test Round is productive, why clean RANDOM-02 is not, and whether a planner change can buy throughput without spending the error budget.

  1. Deadline-aware planner mode

    Add a visible time-budget policy: when the planner approaches its entry deadline, return the last valid joint plan or a safe short-horizon plan instead of waiting for a marginal search improvement.

    Promotion gate: preserve zero planner/schedule/entry-timeout errors across repeated Test Round runs.

  2. Reproducibility envelope

    Q-35/Q-36 show that pinning OMP_NUM_THREADS=1 and Docker to one CPU produced 1,325 tasks twice, with the same binary/config hashes and byte-identical output. Preserve that record, then vary one execution factor at a time to measure how portable the result is.

    Promotion gate: report the full distribution across declared hosts or CPU settings, not only the maximum.

  3. Held-out matrix before optimisation

    Q-37 is the new clean boundary: pinned RANDOM-02 reaches 1,181 versus 1,260 with zero errors. Run the same frozen stack on RANDOM-01, RANDOM-02, and another declared public instance before calling the result a planner improvement.

    Promotion gate: no claim of a general win unless the margin and clean-error condition survive held-out cases.

  4. Scheduler / planner ablation

    Change one layer at a time: task ordering, agent selection, planning window, or collision-resolution strategy. Keep the evaluator and input fixed so a task-count change has a causal explanation.

    Promotion gate: each change gets a named hypothesis, expected direction, and reject/retain decision before the run.

  5. External submission packet

    Once the local result is clean and broad, package the exact source commit, image digest, instance hashes, raw outputs, and reproduction command for organizer-side evaluation.

    Promotion gate: organizer acceptance is the only route to an official leaderboard claim.
Stop rule. Q-35/Q-36 establish a deterministic local baseline only under the recorded pinned runtime; Q-37 shows that this does not transfer to the held-out instance. Close the sampling loop until a planner or scheduler change is declared; more identical Test Round runs can confirm the baseline, but they cannot by themselves create a general algorithmic claim.

Official sources and local audit

LoRR 2024 Benchmark Archive · Start-Kit v2.0.0 · local replay audit · campaign decision ledger

The archive’s 1,186 and 696 values are published references. Local 1,325, 1,318, and 690 values are replay measurements. Q-35/Q-36’s identical hashes support deterministic replay under one pinned runtime, while Q-37’s clean 1,181 held-out result preserves the generalization boundary.

Why the current 3.x Start-Kit is not used for score comparison

The 2024 archive uses an older protocol. Current 3.x adds delayed execution and a different executor pipeline. A run with invented delay settings is useful as a smoke test, but it is not accepted as a 2024 score comparison. The records here therefore pin the tagged v2.0.0 Start-Kit.

Why the published reference stays fixed when a local replay is higher

The archive is the external record. A local evaluator can validate that the source and schema run, but it cannot retroactively modify the organizer’s leaderboard. The clean local claim is a protocol-scoped replay beat pending organizer-side acceptance.
