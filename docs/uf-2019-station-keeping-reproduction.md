# University of Florida VRX 2019 station-keeping reproduction dossier

Status: closest reimplementation design; no historical score reproduction is
claimed.

This dossier records what can be established from the public VRX results,
event-era VRX source, the University of Florida (UF) submission repository,
and UF's own technical documentation. It deliberately separates facts from
source-level deductions and unresolved unknowns. It does not modify or
reimplement benchmark or scorer code.

## Conclusion

The public record is sufficient to identify a defensible closest
reimplementation of UF's station-keeping path:

1. Wait for the VRX task to become ready/running and receive the lat/lon/yaw
   goal.
2. Convert the goal from WGS84 latitude/longitude to the local ENU frame.
3. Send one blind position-and-heading move to the goal.
4. Track the external LQ-RRT trajectory with UF's MRAC wrench controller,
   localization settings, and final VRX-specific gains.
5. Map the wrench through a separate thruster-mapper node.

That is not enough to reproduce the published `0.11` score exactly. The
phase-3 task worlds, the exact Docker/evaluation image, controller-side logs,
and the objects named by UF's final VRX and vrx-docker submodule pointers are
not all available from the current public remotes. The nearest public event-era
scorer source also conflicts with the v1.4 task-description formula. The
correct campaign outcome is therefore a documented reproduction target, not a
promoted controller or record claim.

## 3. Recovered UF submission path

All file references in this section point to the immutable UF tag commit
`7c312eeac2dbaa888adfce5f04ad9a9d85999646`.

### Mission and goal handling

The [station-keeping mission](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/mission_control/navigator_missions/vrx_missions/vrx_station_keeping.py#L16-L23)
does the following:

- waits for a task state of `ready` or `running`;
- obtains the latched `/vrx/station_keeping/goal` message;
- calls `/fromLL` to convert the geographic goal to a local ENU position;
- preserves the goal quaternion for heading; and
- calls `move.set_position(...).set_orientation(...).go(blind=True)`.

The [VRX mission base](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/mission_control/navigator_missions/vrx_missions/vrx.py#L22-L37)
confirms the goal, task-info, conversion-service, and diagnostic topic names.
The station-keeping mission does not read the scorer's pose-error topic to
control the vessel.

### Controller wiring

The [VRX master launch](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/mission_control/navigator_launch/launch/vrx/vrx_master.launch#L5-L30)
starts localization, the separate thruster mapper, the MRAC controller, the
trajectory arbiter, the LQ-RRT path planner, and the VRX mission server. The
[path-planner launch](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/mission_control/navigator_launch/launch/gnc/path_planner.launch#L4-L20)
sets the planner reference topic to `/trajectory/lqrrt`. The master launch
arbitrates that reference to `/trajectory/cmd`, which is the topic consumed by
the MRAC node.

The [released MRAC source](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/gnc/navigator_controller/nodes/mrac_controller.py)
declares this interface:

| Direction | Topic | Message | Source evidence |
| --- | --- | --- | --- |
| Input | `/trajectory/cmd` | `nav_msgs/Odometry` | `use_lqrrt = True` and the subscriber in the controller |
| Input | `/odom` | `nav_msgs/Odometry` | Controller state callback |
| Input | `/wrench/selected` | `std_msgs/String` | Enables or resets adaptation |
| Output | `/wrench/autonomous` | `geometry_msgs/WrenchStamped` | World-to-body wrench publication |
| Output | `pose_ref`, `adaptation`, `~theta` | ROS diagnostic messages | Controller source |

### Final public vehicle configuration

The [final UF sensor config](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/simulation/navigator_gazebo/urdf/navigator_vrx/sensor_config.yaml)

## 4. Source-faithful MRAC design

This is a design transcription of the released controller, not a new
implementation. It is intended to be implementable once the historical ROS,
Gazebo, planner, thruster mapper, and submodule artifacts are restored.

### 4.1 Final VRX parameters

The [final VRX controller launch](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/mission_control/navigator_launch/launch/vrx/vrx_controller.launch#L3-L10)
sets:

| Parameter | Value | Meaning in source |
| --- | --- | --- |
| `kp_body` | `[1000, 1000, 5600]` | Body-frame proportional gains for x, y, yaw |
| `kd_body` | `[1200, 800, 6000]` | Body-frame derivative gains for x, y, yaw |
| `ki` | `[0.1, 0.1, 0.1]` | Disturbance-adaptation rates |
| `kg` | `[5, 5, 5, 5, 5]` | Drag-parameter adaptation rates |
| `~mass` → `mass_ref` | `251.19` kg | Reference-model mass |
| `~izz` → `inertia_ref` | `500.58` kg m² | Reference-model yaw inertia |

The parameter history explains why these values should be treated as final
tag values rather than generic defaults:

| Change | Evidence-backed reading |
| --- | --- |
| [`875453da`](https://github.com/uf-mil/mil/commit/875453da675ee73775282fb8c4e6b4a48b85627d), 21 Oct 2019 | Introduced VRX launch parameters, including mass `251.19`, inertia `500.58`, and an earlier y-gain setting. |
| [`11dca906`](https://github.com/uf-mil/mil/commit/11dca906ff998b947cfb96f144bed64f172526ba), 6 Nov 2019 | Restored the x/y gains to `kp = [1000, 1000, 5600]`, `kd = [1200, 1200, 6000]` after localization changes. |
| [`b45b9f62`](https://github.com/uf-mil/mil/commit/b45b9f62601901181fde02c7458c37cb361dd014), 20 Nov 2019 | Reduced the y derivative gain to `800`; this is the final tag value. |
| [`973cc9c5`](https://github.com/uf-mil/mil/commit/973cc9c56e76421bc77191205ab9dff8b1d08a38), 19 Nov 2019 | Changed station keeping and wayfinding to use `blind=True`. |

### 4.2 Runtime control law

The controller's source-level runtime path is:

1. Read the latest odometry timestamp and use the interval from the previous
   message as `dt`.
2. Convert the measured body-frame velocity to the world frame with the yaw
   rotation `R`.
3. Rotate the diagonal body gains into the world frame:

   ```text
   Kp = R Kp_body Rᵀ
   Kd = R Kd_body Rᵀ
   ```

4. Form the reference-minus-measured error:

   ```text
   p_err = p_ref - p
   yaw_err = yaw(q_ref q_measured⁻¹)
   v_err = v_ref - v
   yaw_rate_err = yaw_rate_ref - yaw_rate
   e = [p_err.x, p_err.y, yaw_err]
   edot = [v_err.x, v_err.y, yaw_rate_err]
   ```

5. Compute the world-frame wrench:

   ```text
   u = Kp e + Kd edot + [mass_ref * ax_ref,
                          mass_ref * ay_ref,
                          inertia_ref * yaw_accel_ref]
       + disturbance_estimate + drag_effort
   ```

   where `drag_effort = clip(Y * theta_estimate, ±[1000, 1000, 1000])`.

6. If the selected wrench is one of `autonomous` or
   `/wrench/autonomous`, adapt only while `||p_err|| < 10 m`:

   ```text
   disturbance_estimate = clip(
       disturbance_estimate + ki * e * dt,
       [-200, -200, -200], [200, 200, 200])
   theta_estimate += kg * Yᵀ(e + edot) * dt
   ```

7. Rotate the world-frame wrench back to the body frame and publish its x/y
   forces and z torque on `/wrench/autonomous`.

The controller's exact five-column regressor `Y` is the one in
[`mrac_controller.py`](https://github.com/uf-mil/mil/blob/7c312eeac2dbaa888adfce5f04ad9a9d85999646/NaviGator/gnc/navigator_controller/nodes/mrac_controller.py#L237-L259),
with `psi` equal to measured yaw, `vx`, `vy` equal to measured world-frame
velocity, and `r` equal to measured yaw rate:

```text
Y = [[vx cos²(psi) + vy sin(psi) cos(psi),
      vx/2 - vx cos(2 psi)/2 - vy sin(2 psi)/2,
      -r sin(psi), -r cos(psi), 0],

     [vy/2 - vy cos(2 psi)/2 + vx sin(2 psi)/2,
      vy cos²(psi) - vx cos(psi) sin(psi),
      r cos(psi), -r sin(psi), 0],

     [0, 0,
      vy cos(psi) - vx sin(psi),
      -vx cos(psi) - vy sin(psi), r]]
```

The source initializes `disturbance_estimate` and `theta_estimate` to zero,
clips the disturbance estimate to ±`[200, 200, 200]`, clips the applied drag
effort to ±`[1000, 1000, 1000]`, and leaves the five-element parameter estimate
itself unclipped. Those are source facts, including the asymmetry in the
limits.

### 4.3 Reference generation boundary

The source sets `use_lqrrt = True` and `use_external_tgen = True`. It therefore
subscribes to the external `/trajectory/cmd` odometry reference, and the
`get_command` path does not call the internal `increment_reference()` method.
The internal method remains part of the released file and contains a
pseudoinverse-based virtual thruster mapper and reference-model drag estimate,
but it is not on the nominal external-trajectory path.

The statement that LQ-RRT is the active reference producer is a source-level
deduction from the controller flag, the trajectory mux in the master launch,
and the planner's `/trajectory/lqrrt` output. It is not a claim that the
historical phase-3 planner emitted identical trajectories without restoring
the missing submodule and dependency versions.

## 5. Scoring semantics: documented versus recovered source

### 5.1 Published task-description semantics

The [v1.4 task description](https://raw.githubusercontent.com/wiki/osrf/vrx/files/VRX2019_Task_Descriptions_v1.4.pdf)
defines the station-keeping run metric as an RMS pose error over position and
weighted heading error, and defines the task score as the mean of the run
scores. It also describes the goal topic and a 1 Hz pose-error publication.
The weighting coefficient `W` is part of the formula, but its phase-3 value is
not stated in the public result table.

### 5.2 Nearest public event-era implementation

The [event-era stationkeeping scorer](https://github.com/osrf/vrx/blob/dd6187ca2eb24838b4288bf1154031556bb73cf6/vrx_gazebo/src/stationkeeping_scoring_plugin.cc)
available in the OSRF source at 22 Nov 2019 instead does the following while
the task is running:

```text
dhdg      = abs(goal_yaw - current_heading)
headError = 1 - abs(dhdg - pi) / pi
poseError = sqrt(dx² + dy²) + headError
total    += poseError
mean     = total / sampleCount
score    = mean
```

The source updates `total` and `sampleCount` on every Gazebo world update. It
publishes the instantaneous and running values on a 1 Hz timer, but the
published cadence is not the accumulation cadence. The source names the
running topic `rms_error` even though the calculation is a running arithmetic
mean of `poseError`.

The scorer history makes the transition explicit:

- [`c0b2e64e`](https://github.com/uf-mil/vrx/commit/c0b2e64e8f209c10daf44790b5d9585543a2094d)
  changed the heading term and removed heading from the squared position
  quantity;
- [`dc95f9db`](https://github.com/uf-mil/vrx/commit/dc95f9dbd19e8b66214524c8e7b6cf91c014d035)
  changed the implementation from RMS to mean pose error;
- [`a664bd97`](https://github.com/uf-mil/vrx/commit/a664bd977bca1c20487c8e833a2f8a599a786d6c)
  removed an extra square root from the mean equation; and
- [`907e0870`](https://github.com/uf-mil/vrx/commit/907e08703e37034ff8360e60fe4e65ac26d8ccf6)
  initialized the running total and corrected the accumulator reference.

The [2019 task tutorial](https://github.com/osrf/vrx/wiki/vrx_2019-task_tutorials)
also warns that the example scorer/API had been modified since the original
competition. Consequently, this dossier preserves both semantics. A future
historical rerun must first establish which scorer binary was used for the UF
phase-3 result; it must not silently substitute either the prose formula or
the nearest source implementation.

### 5.3 Public timing evidence and limits

The event-era generic scorer has defaults of 30 s initial, 60 s ready, and
300 s running. The public 2019 phase-2 stationkeeping worlds explicitly use
10 s initial, 10 s ready, and 300 s running. Those phase-2 values are a useful
bootstrap, not evidence of the hidden phase-3 world values. The official
results page establishes six phase-3 trials but does not publish their world
files, goals, seeds, or timestamps.

## 6. Fact, inference, and unknown register

### Facts established by public artifacts

- UF won the 2019 phase-3 station-keeping task with six displayed scores whose
  mean is `0.11`.
- The UF public phase-3 tag is `7c312eea`, dated 23 Nov 2019, and contains the
  station-keeping mission, MRAC source, launch parameters, localization
  launch, sensor config, thruster config, and two submodule gitlinks.
- The final public UF config has four thrusters, three cameras, one 32-beam
  lidar, and no P3D entry.
- The released mission receives a geographic goal, converts it through
  `/fromLL`, and issues one blind pose-and-heading move.
- The released controller uses external `/trajectory/cmd` odometry and
  publishes an autonomous wrench.
- The nearest public event-era scorer source uses the `poseError`/running-mean
  implementation described above.

### Source-level deductions used by the closest design

- The station-keeping move reaches the MRAC through the trajectory and wrench
  arbiters in the VRX master launch.
- The external reference is supplied by LQ-RRT because the launch topology
  connects `/trajectory/lqrrt` to the controller's `/trajectory/cmd` input.
- `blind=True` is intended to run the move without occupancy-grid checking;
  the released move API labels that mode as dangerous and the station mission
  explicitly selects it.
- The final UF tag was likely the source used for the official submission
  because it is named `vrx-submission-phase3`, is dated immediately before the
  official result announcement, and contains the phase-3 configuration. The
  public artifacts do not prove the exact image digest or that every server
  dependency matched the tag.
- The OSRF `dd6187ca` scorer is the closest public event-era implementation,
  but the unavailable UF VRX gitlink means equivalence to the exact phase-3
  scorer binary is not proven.

### Unknowns that block an exact reproduction claim

- The contents and build provenance of UF VRX gitlink
  `8c204f359effb8ab810fac6b57ebc46d13dcaf3a`.
- The contents and build provenance of UF vrx-docker gitlink
  `5c9928d6d059cf6aef398b9f3bcbc2c1935a3ef4`.
- The phase-3 server/container image digest, compiler/toolchain, and all
  dependency revisions.
- The six phase-3 world files, goal poses, initial poses, wind/wave/fog
  parameters, random seeds, and reset timing.
- Whether the final phase-3 scorer accumulated at every simulator update or
  sampled at 1 Hz, and which of the prose or source formulas was used.
- The official S3 bucket retains task-info ROS bags, server-side Gazebo state
  logs, exact scores, and partial runtime logs. It does not retain the
  generated world SDFs, UF's controller-side trajectory/wrench traces, or the
  image identities needed to replay the trials exactly.

## 7. Reproduction protocol when the missing artifacts are restored

The following procedure is the minimum defensible rerun:

1. Restore the exact UF tag and both submodules at their gitlink identities.
2. Record the OS, ROS, Gazebo, compiler, dependency lock, container digest,
   and SHA-256 manifest before building.
3. Build the server and competitor containers without changing benchmark,
   scorer, WAM-V, or task-definition code.
4. Verify the phase-3 task world and score implementation by source hash and
   runtime log; do not use a public phase-2 world as a phase-3 substitute.
5. Extract every recoverable goal, initial-state, environment, timing, and
   scorer datum from the official S3 logs; distinguish observed values from
   reconstructed ones. Run all six trials only after the remaining inputs are
   pinned, retaining ROS bags, Gazebo logs, task messages, controller
   diagnostics, and per-run scores.
6. Independently recompute the score from raw task outputs using the exact
   recovered scorer and separately compute the v1.4 documented RMS metric.
7. Compare the six reproduced values against the published six-value vector,
   not just against its rounded mean. Any mismatch must be attributed to
   source, world, timing, or numerical differences before tuning a controller.

Until those steps are possible, the only honest label for an implementation
based on this dossier is “closest reimplementation of the public UF
submission,” never “reproduction of UF's 0.11 result.”
