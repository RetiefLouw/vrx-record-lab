Can 100 robots finish more work?

We replayed a published multi-robot result, made the run repeatable, and then tested whether the apparent advantage survived a different scenario.

01 · The challenge

A city-sized puzzle for a team of robots.

The League of Robot Runners (LoRR) is a benchmark for coordinating many agents on a grid. Imagine 100 delivery robots sharing narrow streets. New jobs appear during the run. Every robot needs a legal next move, and the team has a fixed amount of time to complete as many jobs as possible.

The objective

Finish more jobs

The score is simple: how many tasks were completed before the clock stopped. A higher count is better.

The pressure

Move together

Robots can block one another. Assigning a job is not enough—the routes must remain collision-free as the whole team moves.

The constraint

Think on time

The planner gets a small computation budget. A late answer is itself a failure, so speed and quality have to coexist.

03 · Why the repeat matters

Reproducibility is part of the result.

A benchmark number is only useful if we know what produced it. Q-35 and Q-36 repeated the run with a pinned execution condition: one OpenMP thread and one container CPU. Both runs finished cleanly and produced the same compact output hash.

What was held constant
  • ✓Exact public Test Round input
  • ✓LoRR Start-Kit v2.0.0 evaluator
  • ✓Same archived Team RAPID source identity
  • ✓Same image, binary, and configuration hashes
  • ✓Fresh output path for the independent repeat
What the hash tells us

The two compact result files have the same SHA-256 digest:

39525159…6ca88a5b

That supports deterministic replay under this pinned local condition. It does not, by itself, prove that every computer, compiler, or organizer runtime will produce the same count.

04 · The honest limit

A good result also tells us where it stops working.

To test whether the apparent advantage generalized, we ran the same frozen stack on a different public Main Round scenario with 200 agents and 600 ticks. It completed cleanly—but finished fewer tasks than that scenario’s published reference.

05 · What comes next

Turn a replay advantage into an algorithmic one.

The next experiment should change the planner—not keep rerunning the same historical code. The most promising path is to make scheduling aware of crowd density, reuse routes that are still safe, and spend more planning effort where the grid is most congested.

1 · Diagnose

Measure the bottleneck

Compare task delay, route conflicts, planner time, and idle agents on the Test Round and RANDOM-02.

2 · Change one thing

Try density-aware planning

Prioritize assignments and re-planning around crowded corridors while preserving deterministic tie-breaking and a hard deadline.

3 · Earn the claim

Validate on held-out worlds

Require a clean improvement on more than one public instance, then package the exact run for organizer-side review.

LinkedIn draft · no technical background required

What happens when you ask 100 robots to share a city-sized grid and finish as many jobs as possible before the clock runs out? We tested that problem in the League of Robot Runners challenge. The important part was not only getting a bigger number—it was making the result checkable. On the exact public test scenario, our local replay completed 1,325 tasks. The published reference was 1,186. We repeated the run from a fresh output location and got the same 1,325 tasks again, with no recorded planner, scheduling, or entry-timeout errors. That is a +139 local replay margin. It is encouraging evidence, not an official leaderboard change. We also tested a different public scenario. The same frozen setup completed 1,181 tasks against a published reference of 1,260. That result matters just as much: it tells us the first advantage is tied to one instance and should not yet be described as a general algorithmic win. The next step is to change the planner itself—starting with density-aware scheduling and route reuse—and test the change across held-out scenarios. The broader lesson is simple: a credible AI or robotics result needs three things—performance, reproducibility, and an honest account of its limits.
